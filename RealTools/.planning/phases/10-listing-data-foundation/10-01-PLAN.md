<objective>
Add the Supabase data foundation for Brazil-wide listing sourcing: user-owned listings, user-owned import targets, dedupe constraints, RLS policies, indexes, and matching TypeScript Database types.
</objective>

<threat_model>
Threats:
- T10-01-HIGH-01: Creating listings without `user_id` ownership or RLS would expose one broker's sourced listings to another broker.
- T10-01-HIGH-02: Dedupe that is not scoped by user could cause one broker's source URL to block another broker from importing the same public listing.
- T10-01-HIGH-03: Updating `types/supabase.ts` without applying the database migration creates a false-positive build where TypeScript passes but the live DB lacks tables.
- T10-01-MED-01: Over-constraining source/type fields with rigid enums could block later source expansion.
- T10-01-MED-02: Missing indexes on user, source, city/state, and commercial fields could make the MVP feel broken once listings reach hundreds or thousands of rows.

Mitigations:
- Add `user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE` to every new user-owned table.
- Enable RLS on every new table and create owner-scoped policies.
- Use `TEXT` plus `CHECK` constraints only where MVP values are stable; keep commercial type flexible.
- Add user-scoped unique constraints and query indexes.
- Include a `[BLOCKING]` schema push task before the plan can be considered complete.
</threat_model>
